## 1. L'objectif, en une phrase

SonarQube Cloud affiche aujourd'hui **`Coverage: 0 %`** sur un dépôt qui collecte **2 007
tests en CI**. Le but de ce lot est que ce chiffre devienne **vrai**, et qu'il reste vrai à
chaque push. Rien d'autre.

Ce n'est pas Sonar qui se trompe : aucun rapport de couverture n'est produit (pas de
`pytest-cov` dans les `requirements-*.txt`), aucune étape Sonar n'existe dans
`.github/workflows/ci.yml`, et l'analyse tourne donc en **Automatic Analysis** — un mode qui
ne calcule *jamais* la couverture Python, il ne sait que lire un rapport qu'on lui fournit.

## 2. Ce que tu ne peux pas faire — à faire par Alexandre, dans cet ordre

Ces deux actions sont manuelles et **bloquantes** : sans elles, ton travail ne produira
aucun chiffre. Rappelle-les explicitement à la fin de ton compte rendu.

1. **Désactiver l'Automatic Analysis** dans SonarQube Cloud →
   `Yume-Trad > Administration > Analysis Method` → basculer sur *CI-based analysis*.
   Les deux modes sont **mutuellement exclusifs** : tant que l'automatique est actif, le
   scan lancé par la CI est refusé.
2. **Créer le secret `SONAR_TOKEN`** dans GitHub →
   `Settings > Secrets and variables > Actions > New repository secret`, avec un jeton
   généré depuis `My Account > Security` sur SonarQube Cloud.

## 4. Conventions du dépôt — non négociables

Un diff qui les enfreint sera rejeté même s'il fonctionne.

- **Pas de `pyproject.toml`.** Le projet n'est pas empaqueté et ne veut pas l'être
  (`core/version.py`, en-tête de `ruff.toml`). La configuration de couverture va donc dans un
  **`.coveragerc`**, pas ailleurs. `pytest.ini` ne sait pas lire une section coverage.
- **`pytest-cov` va dans `requirements-dev.txt` et nulle part ailleurs.** L'en-tête de ce
  fichier l'écrit noir sur blanc : rien n'en remonte vers `requirements.txt` ni
  `requirements-manga.txt`, la brique manga tient un engagement de légèreté.
- **Commentaires en français, justifiés par une mesure, jamais décoratifs.** Regarde
  `ci.yml`, `pytest.ini` et `ruff.toml` : chaque choix y est défendu par un chiffre constaté
  (« 2 007 tests contre 1 879 », « 564 s → 2,25 s »). Écris dans ce registre. Si tu ne peux
  pas justifier une ligne, ne l'écris pas.
- **Jamais un signal vert qui ne mesure rien.** C'est l'obsession déclarée de ce dépôt, sur
  trois pages de commentaires CI. Elle s'applique intégralement à ce lot : une couverture
  qui omettrait silencieusement la détection manga serait exactement le mensonge que
  `ci.yml` refuse ailleurs. Voir le lot 4.
- **Toute étape de CI doit être rejouable en local**, et documentée dans
  `docs/COMMANDES.fr.md` — la première ligne de `ci.yml` le pose en règle.
- **`windows-latest` fait partie du contrat** pour les jobs de test :
  `tests/conftest.py` fabrique sa planche synthétique avec `C:/Windows/Fonts/msgothic.ttc` et
  *skippe* la fixture si la police manque. Ne migre aucun job de test vers Linux.

## 5. Le travail

### Lot 1 — `.coveragerc` (nouveau fichier, racine)

```ini
[run]
# Chemins RELATIFS, et ce n'est pas cosmétique : les rapports sont produits sur des runners
# Windows et lus par un scanner qui travaille sur un checkout Linux. Un chemin absolu
# `D:\a\Yume-Trad\...` n'est résolu par aucun des deux, et Sonar range alors la couverture
# sous « 0 fichier apparié » sans lever d'erreur — un zéro qui ressemble à un vrai zéro.
relative_files = True

source =
    core
    pipeline
    manga
    scan
    gui
    tools

omit =
    tests/*
    build/*
    sources/*
    manga_models/*

[report]
exclude_also =
    if TYPE_CHECKING:
    raise NotImplementedError
```

Les cinq scripts racine sont volontairement **hors `source`** : ce sont des points d'entrée
minces, les compter ferait bouger le pourcentage sans rien dire du code qui décide. Si tu
constates qu'ils portent de la logique, dis-le dans ton compte rendu — ne l'ajoute pas en
silence.

### Lot 2 — `requirements-dev.txt`

Ajouter `pytest-cov>=5.0`, avec un commentaire court dans le registre du fichier : à quoi il
sert (produire le `coverage.xml` que Sonar lit), et pourquoi il ne remonte pas ailleurs.

### Lot 3 — `sonar-project.properties` (nouveau fichier, racine)

```properties
sonar.projectKey=GNAlexandre_Yume-Trad
sonar.organization=gnalexandre

sonar.sources=core,pipeline,manga,scan,gui,tools,app.py,gui.py,run.py,run_manga.py,run_ocr.py
sonar.tests=tests

sonar.python.version=3.12
sonar.python.coverage.reportPaths=coverage.xml,coverage-banc.xml

sonar.exclusions=build/**,sources/**,manga_models/**,templates/**,**/__pycache__/**
```

⚠ **Piège de nommage.** Le dépôt possède un dossier `sources/` qui contient les œuvres à
traduire — il n'a **rien** à voir avec `sonar.sources`. Il doit être exclu, comme `build/`
qui contient les tomes produits. `ruff.toml` exclut déjà exactement
`build`, `sources`, `manga_models`, `__pycache__` : reste cohérent avec cette liste.

L'énumération explicite de `sonar.sources` est préférée à `sonar.sources=.` justement à
cause de cette collision. Contrepartie : un futur paquet de premier niveau devra être ajouté
ici à la main. Signale-le dans `CONTRIBUTING.md` en une ligne.

### Lot 4 — `.github/workflows/ci.yml`

C'est le lot qui demande du jugement. Trois modifications.

**4a. Le job `tests` produit sa couverture.**
Remplacer la commande de test par l'équivalent avec couverture, en gardant strictement les
mêmes marqueurs exclus :

```yaml
run: pytest -m "not lent and not modeles" -q --cov --cov-report=xml:coverage.xml
```

puis téléverser `coverage.xml` en artefact (`actions/upload-artifact`).

**4b. Le job `banc` produit AUSSI sa couverture.**
Même traitement, sortie `coverage-banc.xml`, artefact séparé.

**C'est le point qui compte, et il faut le commenter comme tel.** Le job `tests` exclut
délibérément `lent` et `modeles`. Si Sonar ne recevait que *ce* rapport, la couverture
publiée exclurait toute la détection de bulles et l'OCR — c'est-à-dire précisément le code
le plus cher et le plus risqué du dépôt — tout en s'affichant comme « la » couverture du
projet. Le dépôt refuse ce genre de demi-mesure partout ailleurs ; il n'y a pas de raison de
l'introduire ici. Deux rapports, fusionnés par Sonar via la liste
`sonar.python.coverage.reportPaths`, donnent le chiffre honnête.

**4c. Un troisième job `sonar`, qui dépend des deux autres.**

```yaml
sonar:
  needs: [tests, banc]
  runs-on: ubuntu-latest    # aucun test ici : le contrat windows-latest ne s'applique pas
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0      # obligatoire : sans historique complet, Sonar ne peut pas
                            # attribuer les lignes ni calculer le « New Code »
    - # récupérer les deux artefacts de couverture à la racine du checkout
    - # lancer l'action de scan officielle
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

**Vérifie la version courante de l'action et son nom** sur
`docs.sonarsource.com` avant de l'écrire : l'ancienne `sonarcloud-github-action` est
dépréciée au profit de `SonarSource/sonarqube-scan-action`, et le numéro de version majeure
bouge. Ne recopie pas une version de mémoire — va la lire.

`needs: [tests, banc]` a une conséquence à assumer : si le banc échoue, aucune analyse n'est
publiée. C'est le comportement voulu — publier une couverture amputée en silence serait pire
qu'une absence de publication.

5. **Compte rendu final** : les deux actions manuelles du §2, plus tout ce que tu as constaté
   et non corrigé.
